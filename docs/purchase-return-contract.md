# Purchase return contract

Source: FR-021 in the billing specification. This contract guides the next database and mobile changes; it does not mark the feature implemented.

An owner or manager selects a received purchase and enters returned quantities by purchase item, a reason, and a supplier credit reference. The command must serialize on the organization row and use the existing actor-scoped command receipt for safe retries. The server validates active membership, original tenant and outlet, positive quantities with at most three decimals, unique lines, and cumulative returned quantity no greater than the original received quantity. It also checks available outlet stock before reversing movements. No client edits an existing purchase or stock row directly.

For each line, derive the returned taxable amount and tax from the original purchase item. Use cumulative proportional rounding: `round(original amount * cumulative returned quantity / received quantity, 2) - previously returned amount`. At a full return the line therefore reverses its original amount exactly. Store the original item, returned quantity, taxable amount, tax, and total as immutable return lines. Record one negative `purchase_return` stock movement per line; update stock balance and version in the same transaction. Recalculate weighted average cost from remaining inventory value if the returned units can be valued safely. If prior sales or adjustments make that cost attribution unreliable, keep the existing average and record the original purchase cost on the return movement; the accounting treatment needs an explicit valuation rule before release.

The return total reduces the supplier bill's net payable. The bill detail must show original total, cumulative returns, cumulative payments, and remaining due. If payments exceed the net payable after return, represent the difference as supplier credit owed to the merchant rather than a negative bill due. A later allocation or refund command must settle that credit; do not silently erase a prior payment. Payment allocation limits must use net payable, and the cash-flow report must distinguish goods returned from cash actually refunded. Repeated commands with the same key and payload return the original return ID; changed payloads fail. Audit and notification entries must use the same transaction.

Mobile acceptance: show returnable quantity and previous returns on purchase detail; prevent excess quantity locally, confirm the credit amount from a server quote or preview, post through one RPC, retain the retry key after an uncertain response, then reload bill, stock, supplier balance and reports. A receipt with no remaining stock must show why return cannot post. The feature is complete only after rollback-only SQL assertions cover retry, over-return, insufficient stock, payment reconciliation, direct-write denial and cross-organization access, followed by device checks.
